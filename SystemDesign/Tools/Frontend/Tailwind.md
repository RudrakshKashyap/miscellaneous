```css
/* =========================================================
   1. BASE LAYER (Compiled First - Top of the file)
   Generic resets, global font rules, native HTML elements.
   ========================================================= */
*,
::before,
::after {
  box-sizing: border-box;
}
body {
  background-color: #f9fafb;
}
h1 {
  font-size: 1.875rem;
}

/* =========================================================
   2. COMPONENTS LAYER (Compiled Second - Middle of the file)
   Complex class bundles, buttons, card layouts.
   ========================================================= */
.btn-primary {
  display: inline-flex;
  background: #2563eb;
}
.dashboard-card {
  border: 1px solid #e5e7eb;
  padding: 1.5rem;
}

/* =========================================================
   3. UTILITIES LAYER (Compiled Last - Absolute bottom of the file)
   Single-purpose overrides (native Tailwind + your custom utils).
   These are native tailwind classes.
   ========================================================= */
.px-3 {
  padding-left: 0.75rem;
  padding-right: 0.75rem;
}
.px-0 {
  padding-left: 0px;
  padding-right: 0px;
}
.mx-auto {
  margin-left: auto;
  margin-right: auto;
}
.scrollbar-none {
  scrollbar-width: none;
}
```

### Why Tailwind Does This (The Architectural Intention)

The entire philosophy of utility-first CSS relies on the idea that an atomic utility class should be the **"final word"** on styling. If you have a component class like `.dashboard-card` that specifies a background color, you should be able to instantly override it inline in your HTML by appending a utility class like `bg-red-500`.

Because the utilities layer sits at the very bottom of the CSS file, the browser's cascade rules ensure that utilities naturally win against base styles and component styles.

### The Problem With Putting Layout Blocks in the Utilities Layer

When you write a multi-utility structural class like `.global-container` and wrap it in `@layer utilities`, you force it into that final bottom block alongside atomic tools like `px-0`.

Because `.global-container` and `.px-0` are now sitting in the same layer, they have the exact same CSS specificity weight. The browser resolves this tie strictly by **Source Order** (whichever class happens to be physically printed lower down inside that utilities block wins).

If your custom `.global-container` gets appended _after_ Tailwind's native padding utilities during the compilation process, the browser reads your file like this:

```css
/* ... native utilities ... */
.px-0 {
  padding-left: 0;
  padding-right: 0;
}

/* ... your custom utility at the end ... */
.global-container {
  max-width: 80rem;
  padding-left: 1rem;
  padding-right: 1rem;
}
```

When you write `<div class="global-container px-0">`, the browser looks at the stylesheet, sees `.global-container` closer to the bottom of the file, and **ignores `px-0` completely**. Your page wrapper will refuse to go flush with the screen.

### Summary

By moving `.global-container` out of utilities and into `@layer components`, you push it into the middle block of the file tree. This guarantees that _every single utility_ generated by Tailwind sits beneath it, ensuring that inline overrides like `px-0`, `max-w-none`, or `m-0` will always work perfectly on your pages.

Yes, **`tailwind-merge` (`twMerge`) can absolutely drop your custom classes—or silently drop native Tailwind classes because of them.** However, this only happens under very specific naming conditions.

To understand why this happens and how to prevent it, you have to understand the core rule of how `tailwind-merge` works: **It only deletes a class if it thinks that class belongs to a "conflict group" where a later class overrides it**.

Here is exactly how it handles different types of custom styles:

---

### Scenario 1: Raw, Vanilla Custom CSS Classes (100% Safe) ✅

If you use a plain CSS class name that does not borrow or mimic Tailwind's default utility prefixes, `tailwind-merge` will **never** touch it. It has no idea what the class means, sees no conflict group for it, and leaves it completely alone.

```javascript
// Result: "my-custom-card flex p-6"
twMerge("my-custom-card flex p-4", "p-6");
```

_`.my-custom-card` is entirely unrecognized by Tailwind's core group mapping, so it is safely preserved._

---

### Scenario 2: Custom Utilities Using Tailwind Prefixes (Dangerous!) ⚠️

If you create custom utility classes that begin with standard Tailwind prefixes like `text-`, `font-`, `bg-`, or `p-`, **you enter the danger zone.** `tailwind-merge` operates entirely on string pattern heuristics. If it gets confused, things get silently dropped in one of two ways:

#### A. Your custom style gets dropped:

Imagine you create a custom class in your CSS file called `.text-body` to handle a specific font-size and line-height fallback combo.

```javascript
// Intended Result: "text-body text-blue-500" (You want body size + blue color)
// ACTUAL Result: "text-blue-500" ❌
twMerge("text-body", "text-blue-500");
```

**Why it happened:** `tailwind-merge` scans the string and sees two classes starting with `text-`. It assumes they are modifying the exact same property (text color or size), decides that the second one wins, and **wipes your custom `.text-body` out of existence**.

#### B. A native Tailwind style gets dropped:

Imagine you create a custom class called `.text-biggest` to represent a massive hero text size.

```javascript
// Intended Result: "text-gray-800 text-biggest"
// ACTUAL Result: "font-bold text-biggest" ❌ (Gray color is lost!)
twMerge("font-bold text-gray-800", "text-biggest");
```

**Why it happened:** `tailwind-merge` doesn't know that your custom `text-biggest` class only alters font-size. It sees `text-gray-800` followed by another `text-` utility and assumes `text-biggest` is meant to overwrite the color choice, stripping `text-gray-800` out.

---

### What About Custom Font Families (`font-brand`)?

Font utilities are notoriously tricky because the `font-` prefix is heavily overloaded in Tailwind (it handles `font-bold` [weight], `font-sans` [family], and in older configurations, font-size scales).

- **In Tailwind v3:** If you add a custom font family like `font-brand` to your config, `tailwind-merge` does not automatically know that `brand` belongs to the font-family group. It might fail to resolve conflicts against `font-sans`, leaving _both_ applied, or it might treat it as a weight and drop a native weight class by mistake.
- **In Tailwind v4:** Because Tailwind v4 natively uses CSS variables for design tokens (`--font-brand`), modern versions of `tailwind-merge` (v3.0+) are smarter and map these namespaces automatically, making custom fonts significantly safer out of the box.

---

### How to Fix It: Extend the Config

If you are running into bugs where your custom font families or custom `text-` layout overrides are vanishing, you must stop using the default `twMerge` import and create an **[extended custom merge function](https://github.com/dcastil/tailwind-merge/blob/main/docs/configuration.md#extending-the-tailwind-merge-config)** that registers your custom keys
